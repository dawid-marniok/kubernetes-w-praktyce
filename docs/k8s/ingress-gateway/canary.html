Canary: jak HTTPRoute dzieli ruch

W HTTPRoute wpisujesz weight: 90 i weight: 10. Czy to losowanie? Czy użytkownik zostaje na jednej wersji? Sprawdziliśmy na naszym klastrze, a poniżej możesz to przeklikać w symulatorze.

1Krótko

Wagi dzielą żądania, nie użytkowników. Traefik (nasz kontroler Gateway API) rozdziela każde żądanie osobno, po kolei według wag: weighted round robin. Nie losuje i nic nie pamięta o użytkowniku. Przy 90/10 co dziesiąte żądanie idzie do v2, niezależnie od tego, kto je wysłał.

2Jak płynie ruch

# przyklady/k8s/07-gateway-api/httproute-canary.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: przyklad-canary
spec:
  parentRefs: [{name: przyklad-gw}]
  hostnames: [gw-trener.k8s.marniok.dev]
  rules:
  - backendRefs:
    - {name: web-v1, port: 80, weight: 90}
    - {name: web-v2, port: 80, weight: 10}

Wagi to proporcje, nie procenty: 9 i 1 działa tak samo jak 90 i 10. Waga 0 wyłącza backend z ruchu.

Ten sam test z włączonymi ciasteczkami (curl -c plik -b plik) daje identyczny wzór, a Traefik nie ustawia żadnego ciasteczka. Sesji nie ma.

Licznik ma każda instancja Traefika osobno. U nas jest jedna replika, więc rytm jest idealny. Przy kilku replikach (a NLB rozrzuca połączenia między nie) z zewnątrz wygląda to mniej regularnie, ale proporcja zostaje ok. 90/10.

4Symulator

Trzech użytkowników wysyła żądania na zmianę przez ten sam Gateway. Algorytm jest ten sam co w Traefiku: jeden wspólny licznik, kolejne żądanie dostaje backend według wag.

Na co patrzeć: każdy z trzech użytkowników co jakiś czas dostaje v2, choć „przydział” był 10%. Z włączonym nagłówkiem żądania Ani omijają wagi i nie zajmują miejsca w kolejce, więc pozostali dalej dostają 90/10.






  
5Co z tego wynika

  

    

      Dobrze działa dla:
      
    
        
  • API bez stanu, gdzie każde żądanie jest niezależne,
    • 
        
  • usług wewnętrznych i backendów, na które patrzy się przez metryki (błędy, opóźnienia v2 vs v1),
    • 
        
  • szybkiego i odwracalnego przełączenia: zmiana wag, bez restartu podów.
    • 
      

    

    

      Uważaj przy:
      
    
        
  • aplikacjach webowych: HTML z v1, a plik JS lub CSS z v2, i strona się sypie,
    • 
        
  • zmianach widocznych dla użytkownika: nowy przycisk raz jest, po odświeżeniu go nie ma,
    • 
        
  • sesji w pamięci poda: logowanie na v1, kolejne żądanie na v2 nie zna sesji.
    • 
      

    

  

  
„10% użytkowników widzi nową wersję” wymaga czegoś więcej niż wag: dopasowania po nagłówku lub ciasteczku albo sesji (sticky).






  
6Testerzy po nagłówku

  
Dopasowanie po nagłówku (i po ciasteczku, bo to też nagłówek Cookie) jest w standardowym kanale Gateway API. Reguła z matches wygrywa z regułą bez dopasowania, więc testerzy zawsze trafiają w v2, a reszta dzieli się wagami.


rules:
- matches:                                # testerzy: zawsze v2
  - headers: [{name: X-Canary, value: "true"}]
  backendRefs: [{name: web-v2, port: 80}]
- backendRefs:                            # wszyscy inni: wagi
  - {name: web-v1, port: 80, weight: 90}
  - {name: web-v2, port: 80, weight: 10}


curl -s https://gw-trener.k8s.marniok.dev | grep ^Name                       # 90/10
curl -s -H "X-Canary: true" https://gw-trener.k8s.marniok.dev | grep ^Name   # zawsze web-v2

  
Wariant „po ciasteczku”: aplikacja albo zespół ustawia testerom np. canary=always, a reguła dopasowuje nagłówek Cookie wyrażeniem regularnym (type: RegularExpression, wsparcie zależy od kontrolera).

8Plan wdrożenia canary

  
    
    
  1. v2 obok v1: nowy Deployment i Service, w HTTPRoute waga v2 = 0. Nikt jej nie widzi.
    2. 
    
  2. Testerzy: reguła z nagłówkiem lub ciasteczkiem. Sprawdzają wewnętrzni.
    3. 
    
  3. 90/10: mały kawałek prawdziwego ruchu. Patrzysz na błędy 5xx i opóźnienia v2 w porównaniu z v1.
    4. 
    
  4. 50/50, potem 0/100: po każdym kroku chwila obserwacji.
    5. 
    
  5. Sprzątanie: v2 zostaje jedyną wersją, stary Deployment i reguła z nagłówkiem znikają.
    6. 
  

  
Rollback to powrót do 100/0 jedną komendą. Pody v2 dalej działają, więc możesz zbadać, co poszło nie tak.






  
9Komendy


# kolejność odpowiedzi (1 = v1, 2 = v2)
for i in $(seq 30); do curl -s https://gw-<login>.<DOMENA> | grep ^Name | sed 's/Name: web-v//'; done | tr '\n' ' '; echo

# suma na 100 żądaniach
for i in $(seq 100); do curl -s https://gw-<login>.<DOMENA> | grep ^Name; done | sort | uniq -c

# na żywo: terminal 1
while true; do curl -s https://gw-<login>.<DOMENA> | grep ^Name; sleep 0.5; done

# terminal 2: przesuń wagi
kubectl patch httproute przyklad-canary --type merge -p \
'{"spec":{"rules":[{"backendRefs":[{"name":"web-v1","port":80,"weight":50},{"name":"web-v2","port":80,"weight":50}]}]}}'

# co aktualnie jest w HTTPRoute
kubectl get httproute przyklad-canary -o jsonpath='{range .spec.rules[*].backendRefs[*]}{.name}={.weight}{"\n"}{end}'

  
Uwaga: kubectl patch --type merge podmienia całą listę rules. Jeśli masz regułę z nagłówkiem, zmieniaj wagi przez edycję pliku i kubectl apply.
