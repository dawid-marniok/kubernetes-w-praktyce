1 Droga żądania: od przeglądarki do poda

Wszystkie hosty pod domeną szkolenia prowadzą do jednego load balancera i jednego Traefika. Dopiero Traefik, po nazwie hosta i ścieżce, wybiera Twój Service. Kliknij ogniwo, żeby zobaczyć, co robi i jak je sprawdzisz. Przełącznik pokazuje, co wymienia się na własnych serwerach.

2 Jak cert-manager wystawia certyfikat (HTTP-01)

Do Ingressu dopisujesz adnotację i sekcję tls. Resztę robią cert-manager i Let's Encrypt. Na naszym klastrze trwa to ok. 30 s. Wyniki w krokach pochodzą z testu na klastrze 20.10.2026 (host lab08test.k8s.marniok.dev). Kliknij krok albo użyj przycisków; „odtwórz” przechodzi przez wszystkie kroki sam.

  1. Ingress z adnotacją. Dopisujesz cert-manager.io/cluster-issuer: letsencrypt-prod i sekcję tls z tym samym hostem co w rules oraz secretName: lab08-web-tls. kubectl apply. 
    $ kubectl apply -f moje/lab08-ingress.yaml
ingress.networking.k8s.io/lab08-web configured
  2. Certificate i CertificateRequest. Część cert-managera zwana ingress-shim widzi adnotację i tworzy Certificate o nazwie jak Secret. Secretu jeszcze nie ma, więc cert-manager generuje klucz prywatny i tworzy CertificateRequest z CSR. 
    $ kubectl describe certificate lab08-web-tls
  Normal  Issuing    Issuing certificate as Secret does not exist
  Normal  Generated  Stored new private key in temporary Secret resource "lab08-web-tls-dtm8z"
  Normal  Requested  Created new CertificateRequest resource "lab08-web-tls-1"
  3. Order w Let's Encrypt. ClusterIssuer jest typu ACME, więc cert-manager składa Order. Let's Encrypt odpowiada: udowodnij, że kontrolujesz ten host, metodą HTTP-01. Oto token. 
    $ kubectl get order
NAME                        STATE     AGE
lab08-web-tls-1-377731385   pending   4s
  4. Challenge, pod solvera i tymczasowy Ingress. cert-manager tworzy Challenge, a w Twoim namespace pod cm-acme-http-solver-… (port 8089) z Service i tymczasowy Ingress na ścieżkę /.well-known/acme-challenge/<token> dla Twojego hosta. 
    $ kubectl get challenge
NAME                                  STATE     DOMAIN                      AGE
lab08-web-tls-1-377731385-556202022   pending   lab08test.k8s.marniok.dev   2s
$ kubectl get pods,ingress | grep acme
pod/cm-acme-http-solver-qcqm6                         1/1   Running   0   2s
ingress.networking.k8s.io/cm-acme-http-solver-9hfwd   traefik   lab08test.k8s.marniok.dev   …elb.eu-central-1.amazonaws.com   80   2s
  5. Self-check. Zanim cert-manager zgłosi gotowość, sam pobiera token tą samą drogą co świat: DNS, NLB, Traefik, tymczasowy Ingress, pod solvera. Gdy NetworkPolicy odcina solver albo DNS jeszcze nie wskazuje na klaster, proces stoi tutaj. 
    $ kubectl describe challenge <nazwa>     # tylko gdy coś nie działa
  Reason: Waiting for HTTP-01 challenge propagation: failed to perform self check GET request …
  6. Let's Encrypt sprawdza token. Serwer Let's Encrypt łączy się z internetu na port 80 Twojego hosta i pobiera token. Ruch idzie przez NLB i Traefika do poda solvera. Token się zgadza, więc wyzwanie i zamówienie są zaliczone. 
    GET http://lab08test.k8s.marniok.dev/.well-known/acme-challenge/<token>
  → NLB → Traefik → tymczasowy Ingress → pod solvera → 200 + token
$ kubectl get challenge        # STATE valid, po chwili obiekt znika
  7. Secret z certyfikatem. cert-manager pobiera podpisany certyfikat i zapisuje go z kluczem w Secrecie lab08-web-tls (typ kubernetes.io/tls). Certificate dostaje READY True. Pod solvera i tymczasowy Ingress są usuwane. 
    $ kubectl get certificate
NAME            READY   SECRET          AGE
lab08-web-tls   True    lab08-web-tls   27s
$ kubectl get secret lab08-web-tls
NAME            TYPE                DATA   AGE
lab08-web-tls   kubernetes.io/tls   2      27s
  8. Traefik serwuje certyfikat. Traefik widzi Secret wskazany w spec.tls i pokazuje ten certyfikat każdemu, kto w TLS (SNI) prosi o Twój host. Za ok. 60 dni cert-manager sam przejdzie te kroki jeszcze raz (odnowienie ok. 30 dni przed końcem ważności). 
    $ curl -sI https://lab08test.k8s.marniok.dev | head -1
HTTP/2 200
$ openssl s_client … | openssl x509 -noout -issuer -dates
issuer=C=US, O=Let's Encrypt, CN=YR2
notBefore=Oct 20 04:10:58 2026 GMT
notAfter=Jan 18 04:10:57 2027 GMT
On-prem: kroki 3–6 wymagają, żeby Let's Encrypt dosięgnął Twojego hosta z internetu. Klaster w firmowej sieci zwykle tego nie ma. Wtedy DNS-01 (token w rekordzie TXT, do klastra nikt się nie łączy) albo firmowe CA: Certificate → CertificateRequest → od razu Secret, bez Order i Challenge. Szczegóły: cert-manager.md.

3 Typy Service: co naprawdę powstaje w AWS

Każdy kolejny typ jest nadbudową poprzedniego: NodePort to ClusterIP plus port na węzłach, LoadBalancer to NodePort plus load balancer przed węzłami. Wyniki z naszego klastra, 20.10.2026.

ClusterIP

domyślny · wirtualny adres w klastrze

Skąd dojdziesz

  • pod w klastrze tak
  • maszyna w VPC nie
  • laptop / internet nie

Co tworzy w AWS

Nic. Adres nie należy do żadnej maszyny: pakiet przechwytują reguły kube-proxy na węźle klienta.

U nas

Podstawa wszystkiego. Za Twoim Ingressem stoi właśnie ClusterIP lab08-web.

$ kubectl get svc lab08-web
TYPE        CLUSTER-IP     PORT(S)
ClusterIP   172.20.x.x     80/TCP
NodePort

ClusterIP + port 30000–32767 na każdym węźle

Skąd dojdziesz

  • pod w klastrze tak
  • maszyna w VPC tak
  • laptop / internet nie

Co tworzy w AWS

Nic. Port otwiera się na wszystkich 3 węzłach, także tam, gdzie nie ma Twojego poda.

U nas

Węzły stoją w prywatnych podsieciach, bez publicznych adresów. Z poda działa, z laptopa nie.

$ kubectl get svc lab08-web-np
TYPE       PORT(S)
NodePort   80:30281/TCP
$ kubectl exec deploy/lab08-web -- curl -s -o /dev/null \
    -w '%{http_code}\n' http://<INTERNAL-IP węzła>:30281
200
LoadBalancer

NodePort + load balancer AWS przed węzłami

Skąd dojdziesz

  • pod w klastrze tak
  • maszyna w VPC tak
  • laptop / internet tak

Co tworzy w AWS

Bez adnotacji Classic Load Balancer, z aws-load-balancer-type: nlb Network Load Balancer. Do tego security group k8s-elb-… i reguła w SG węzłów. Tworzy je service-controller w control plane EKS.

Przebieg (Classic LB)

  1. 0 s EnsuringLoadBalancer, Kubernetes przydziela NodePort 30586
  2. ~5 s EnsuredLoadBalancer, w EXTERNAL-IP nazwa a3b8…-1968439010.eu-central-1.elb.amazonaws.com
  3. potem listener TCP:80 → 30586 na 3 instancjach, health check TCP:30586, na początku OutOfService
  4. ~1 min 40 s strona odpowiada z internetu (DNS + health check)
  5. delete LB i security group znikają po ok. 12 s

U nas

Każdy taki Service to osobny LB płatny za godzinę. Dlatego jest jeden: Traefik za NLB, a aplikacje wystawiamy Ingressem.

headless (clusterIP: None) — bez wirtualnego adresu. DNS zwraca od razu adresy podów. Używa go StatefulSet (dzień 3).
ExternalName — tylko rekord CNAME do nazwy spoza klastra, np. api.example.com. Bez proxy, portów i selektora.
Adnotacja aws-load-balancer-scheme: internal — LB dostaje adres prywatny, dostępny tylko z VPC.
AWS Load Balancer Controller (na k8s-sages go nie ma) — NLB z celami IP podów zamiast NodePortów i ALB jako kontroler Ingress (klasa alb).

4 Ingress a Gateway API: kto co tworzy

Ingress to jeden obiekt, w którym zespół aplikacji wpisuje wszystko: host, ścieżki, TLS i adnotacje kontrolera. Gateway API rozdziela to na trzy obiekty dla trzech ról. Ramką zaznaczony jest obiekt, który piszesz Ty.

Ingress

Administrator
IngressClass traefiki sam kontroler (Traefik) w ns traefik
↑ ingressClassName
Zespół aplikacji
Ingresshost, ścieżki, backend, tls, adnotacja cert-managera, adnotacje kontrolera (rewrite, redirect)
↓ backend.service
Servicew Twoim namespace

Gateway API

Dostawca kontrolera
GatewayClass traefikktóry kontroler obsługuje bramy; instaluje się z kontrolerem
↑ gatewayClassName
Zespół platformy
Gatewaylistenery (u Traefika porty 8000/8443), hosty, TLS z certificateRefs i adnotacją cert-managera, allowedRoutes: kto może się podpiąć
↑ parentRefs
Zespół aplikacji
HTTPRoutehostnames, matches (ścieżka, nagłówki, metoda), filters (URLRewrite, RequestRedirect), backendRefs z wagami
↓ backendRefs
Servicew Twoim namespace; z innego wymaga ReferenceGrant
SprawaIngressGateway API
Certyfikatkażdy Ingress osobno: adnotacja + spec.tlsraz, na listenerze Gatewaya; HTTPRoute o TLS nie wie
Canary, nagłówki, rewriteadnotacje albo Middleware konkretnego kontroleraw specyfikacji, takie same dla każdego kontrolera
Kto może wystawić hostkażdy, kto ma prawo tworzyć IngressGateway decyduje (allowedRoutes, hostname)
Statuskolumna ADDRESSwarunki Accepted, ResolvedRefs, Programmed
Na k8s-sagesdziała, ćwiczysz w lab08nie jest domyślnie włączone (CRD trzeba doinstalować); pokazuje prowadzący w demie

Gotowe manifesty Gateway i HTTPRoute: przyklady/k8s/07-gateway-api/. Czy klaster ma CRD Gateway API: kubectl get crd | grep gateway.networking.k8s.io.

5 Komendy: sprawdzasz od końca

kubectl get pods -l app=lab08-web -o wide

Pody Running i READY 1/1? Bez readiness pod nie dostaje ruchu.

kubectl get endpointslices \
  -l kubernetes.io/service-name=lab08-web

Adresy gotowych podów. Pusto = selektor albo readiness, Traefik zwraca 503.

kubectl describe svc lab08-web

Selector, Port, TargetPort. Zły targetPort daje 502.

kubectl describe ingress lab08-web

Klasa, host, backend z IP podów, zdarzenia. ADDRESS = nazwa NLB.

kubectl get certificate,order,challenge
kubectl describe challenge <nazwa>

Stan certyfikatu. Gdy wisi, odpowiedź jest zwykle w describe challenge.

dig +short <login>.k8s.marniok.dev
curl -sI https://<login>.k8s.marniok.dev
