Jak klaster wie, kim jesteś

1 Jedna zasada: dowód → tożsamość → RBAC

Uwierzytelnienie ma jeden wynik: nazwę użytkownika i listę grup. Tylko to trafia dalej. RBAC nie wie, czy przyszedłeś z certyfikatem, z Keycloaka czy z IAM. Widzi napis anna i grupy, i szuka bindingów dla nich.

Sprawdzisz to w każdym klastrze jedną komendą: kubectl auth whoami pokazuje nazwę i grupy, które zobaczył apiserver.

2 Krok po kroku obok siebie

Po lewej zwykły Kubernetes (np. postawiony przez kubeadm), po prawej EKS, czyli nasz klaster. Wybierz sposób logowania po obu stronach i przechodź krokami.

3 Zwykły Kubernetes: trzy drogi

W klastrze, który stawiasz sam, decydujesz flagami kube-apiservera, które metody są włączone. Najczęściej spotkasz trzy.

Certyfikat klienta x509

  • CN = nazwa użytkownika, każde O = grupa.
  • apiserver ufa certyfikatom podpisanym przez CA z flagi --client-ca-file. Innego podpisu nie przyjmie.
  • Klucz CA ma administrator; na klastrach zarządzanych go nie masz, więc podpisujesz przez API CertificateSigningRequest (krok po kroku).
  • Nie da się go unieważnić. Kubernetes nie sprawdza list CRL. Wyciekł = działa do daty ważności, chyba że wymienisz CA całego klastra. Dlatego krótka ważność.
  • O=system:masters omija RBAC całkowicie. Takiego certyfikatu nie wyłączysz żadnym bindingiem.

OIDC (logowanie firmowe)

  • apiserver ufa wystawcy tokenów: Keycloak, Dex, Entra ID, Google, GitLab. Konfiguracja flagami --oidc-* albo plikiem --authentication-config.
  • W kubeconfigu jest wtyczka exec, zwykle kubelogin (kubectl oidc-login): otwiera przeglądarkę, logujesz się, dostaje token.
  • Claim (np. email) → nazwa, claim groups → grupy. Zwykle z prefiksem, np. oidc:.
  • Odebranie dostępu: wyłączasz konto u wystawcy, a wydany token wygasa sam (zwykle po kilku–kilkudziesięciu minutach, zależnie od wystawcy). To standard dla ludzi.

Token ServiceAccount

  • JWT podpisany kluczem klastra (--service-account-key-file). Tak loguje się każdy pod.
  • Można go wyjąć na zewnątrz: kubectl create token <sa>. Dobre dla automatów, złe dla ludzi (wspólne konto, brak MFA, brak śladu, kto to był).
  • Nazwa: system:serviceaccount:<ns>:<sa>. Usunięcie SA unieważnia jego tokeny.

Rzadziej: plik statycznych tokenów, webhook sprawdzający token w zewnętrznej usłudze, proxy uwierzytelniające (nagłówki X-Remote-User). Na klastrze z kubeadm plik admin.conf to certyfikat w grupie kubeadm:cluster-admins (zbindowanej do cluster-admin), a awaryjny super-admin.conf ma O=system:masters.

Certyfikat dla człowieka to wyjątek, nie reguła. Nadaje się na konto awaryjne albo do nauki. Do codziennej pracy zespołu: OIDC z firmowym logowaniem, grupy z katalogu i RoleBinding na grupę, nie na osobę.

4 EKS: IAM, access entries i access policies

Na EKS nie dostajesz certyfikatu ani hasła do klastra. Logujesz się do AWS, a EKS zamienia tożsamość IAM na nazwę użytkownika Kubernetesa.

  1. aws eks update-kubeconfig zapisuje w kubeconfigu wtyczkę exec: aws eks get-token --cluster-name k8s-sages. W pliku nie ma żadnego sekretu.
  2. Przy każdym żądaniu kubectl uruchamia tę komendę. AWS CLI podpisuje Twoimi poświadczeniami (sesja aws login) zapytanie do STS „kim jestem” i pakuje je w token k8s-aws-v1.…, ważny kilkanaście minut.
  3. EKS wysyła to zapytanie do STS i dostaje ARN, np. arn:aws:iam::<konto>:user/szkolenie/anna.
  4. EKS szuka access entry dla tego ARN. Wpis mówi: nazwa użytkownika w Kubernetesie (anna) i opcjonalnie grupy. Brak wpisu = 401, mimo poprawnego konta AWS.
  5. Dalej zwykły RBAC na anna i jej grupy. Plus jedno, czego nie ma w zwykłym Kubernetesie: access policies.

Access policies: uprawnienia, których nie widać w klastrze

Do access entry można przypiąć gotową politykę EKS, z zasięgiem na cały klaster albo na wybrane namespace'y: AmazonEKSClusterAdminPolicy, AmazonEKSAdminPolicy, AmazonEKSEditPolicy, AmazonEKSViewPolicy (lista: aws eks list-access-policies). Odpowiadają mniej więcej cluster-admin, admin, edit i view. Sprawdza je osobny autoryzator EKS (webhook) obok RBAC, a uprawnienia z obu źródeł się sumują.

Konsekwencje, o które się potkniesz

  • kubectl get clusterrolebindings nie pokaże, skąd ktoś ma admina. Na naszym klastrze trener nie ma żadnego bindingu, a może wszystko.
  • kubectl auth can-i --list nie widzi access policies i ostrzega: Warning: the list may be incomplete: webhook authorizer does not support user rule resolution.
  • --as / --as-group wymusza sam RBAC: impersonowany użytkownik nie dostaje access policies.
  • Pełny obraz: aws eks list-access-entries i aws eks list-associated-access-policies, czyli po stronie AWS, nie kubectl.

aws-auth: stary sposób

  • Wcześniej mapowanie IAM → użytkownik było w ConfigMapie aws-auth w kube-system. AWS oznacza go jako przestarzały (deprecated).
  • Tryb ustawia authenticationMode klastra: CONFIG_MAP, API_AND_CONFIG_MAP albo API (tylko access entries).
  • k8s-sages działa w trybie API: ConfigMapy aws-auth w ogóle nie ma.
  • Access entry zarządzasz przez API AWS (CLI, Terraform), więc literówka nie odetnie całego klastra jak zepsuty YAML w aws-auth.

Certyfikaty klienta na EKS: zobacz README. W skrócie: EKS nie podpisuje certyfikatów do logowania (sprawdzone na k8s-sages), ludzie przychodzą przez IAM.

6 AKS i GKE w skrócie

AKS (Azure)

  • Logowanie przez Microsoft Entra ID; w kubeconfigu wtyczka exec kubelogin (od Azure).
  • Autoryzacja: zwykły RBAC (w subjects użytkownicy i grupy z Entra ID) albo „Azure RBAC for Kubernetes”: przypisania ról w Azure, sprawdzane webhookiem. To odpowiednik access policies z EKS.
  • Konto lokalne z certyfikatem admina (az aks get-credentials --admin) da się wyłączyć: --disable-local-accounts.

GKE (Google Cloud)

  • Logowanie kontem Google; w kubeconfigu wtyczka exec gke-gcloud-auth-plugin.
  • Nazwa użytkownika to e-mail konta (człowieka albo service account Google).
  • Autoryzacja: IAM projektu i RBAC klastra działają razem. Wystarczy, że jedno z nich pozwala.
