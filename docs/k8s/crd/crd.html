Jak działa CRD

CustomResourceDefinition dopisuje do API Kubernetesa nowy typ obiektu. kube-apiserver od razu go obsługuje: REST, walidacja, RBAC, zapis w etcd, kubectl get. Żeby obiekt coś robił, potrzebny jest kontroler. CRD + kontroler = operator.

  • kind: Backup · skrót bk
  • CRD bez kontrolera = rekord w etcd
  • watch → porównaj → działaj
  • cert-manager · CloudNativePG

1 Cały obraz w pięciu strzałkach

Wbudowane typy (Pod, Deployment, Service) kube-apiserver zna od startu. CRD to zwykły obiekt w API, który mówi: od teraz istnieje typ Backup w grupie szkolenie.example.com, z takimi polami. Strzałki 1–3 obsługuje sam kube-apiserver. Strzałki 4–5 to osobny program: kontroler.

  1. CRD (strzałka 1). Trener wgrywa crd-backup.yaml. kube-apiserver rejestruje nowy endpoint i ogłasza go w discovery.
  2. Obiekt (strzałki 2–3). Ty wgrywasz Backup nightly. Bramki jak dla Poda, potem walidacja schematem z CRD, zapis w etcd. Koniec.
  3. Kontroler (strzałki 4–5). Program, który obserwuje obiekty Backup, porównuje stan zadany z rzeczywistym, tworzy CronJob i zapisuje status.
  4. Operator. Ten sam wzorzec z wiedzą o konkretnej aplikacji: cert-manager (Certificate → Secret TLS), CloudNativePG (Cluster → pody, PVC, Service'y).

2 Symulator: CRD, obiekt, kontroler

Ty to kursantka anna z namespace'em anna. W namespace bartek pracuje inny kursant. Klikaj krok dalej, żeby przejść scenariusz z labu, albo wywołuj akcje w dowolnej kolejności, np. wgraj obiekt przed CRD albo usuń CRD z włączonym kontrolerem.

Spróbuj: zanim trener wgra CRD, kliknij apply nightly. kubectl nie znajdzie typu w discovery i nie wyśle żądania: no matches for kind "Backup", ensure CRDs are installed first.
Spróbuj: włącz kontroler, zmień schedule, wyłącz kontroler i zmień jeszcze raz. Backup i CronJob się rozjeżdżają i nikt tego nie naprawia. Włącz kontroler: zgodność wraca w jednym przebiegu pętli.

3 Pętla kontrolera

Kontroler to zwykły program w podzie (zwykle Deployment z jedną aktywną repliką i leader election), który rozmawia z kube-apiserverem przez swój ServiceAccount. Działa tak samo jak wbudowane kontrolery z kube-controller-manager: nie wykonuje polecenia raz, tylko bez końca doprowadza świat do tego, co jest w spec.

Co kontroler robi w jednym obiegu

  1. Obserwuj. Watch na backups we wszystkich namespace'ach i na CronJobach, które utworzył. Każda zmiana wrzuca klucz <ns>/<nazwa> do kolejki.
  2. Porównaj. Czyta aktualny Backup i CronJob. Patrzy na stan, nie na samo zdarzenie (level-triggered), więc zgubione zdarzenie nie psuje wyniku.
  3. Działaj. Tworzy albo poprawia CronJob z ownerReferences wskazującym na Backup. Zapisuje status przez /status, m.in. observedGeneration.
  4. Błąd? Klucz wraca do kolejki z rosnącym opóźnieniem. Działanie jest idempotentne: drugi obieg na zgodnym stanie nic nie zmienia.

metadata.generation rośnie przy każdej zmianie spec. Gdy status.observedGeneration jest równe generation, kontroler przetworzył najnowszą wersję.

Usunięcie Backupu usuwa CronJob bez udziału kontrolera: robi to garbage collector w kube-controller-manager na podstawie ownerReferences.

Ty piszesz spec

apiVersion: szkolenie.example.com/v1
kind: Backup
metadata:
  name: nightly
  generation: 1           # nadaje kube-apiserver
spec:
  schedule: "0 2 * * *"
  retention: 7

Kontroler pisze status i CronJob

status:                   # przez /status, wymyślone pola
  cronJob: nightly-backup
  observedGeneration: 1
---
kind: CronJob
metadata:
  name: nightly-backup
  ownerReferences:
  - kind: Backup
    name: nightly
spec:
  schedule: "0 2 * * *"

4 Ten sam wzorzec w narzędziach, które znasz

Instalujesz narzędzie = instalujesz zestaw CRD, kontroler w Deploymencie i RBAC dla kontrolera (zwykle jednym helm install). Ty piszesz krótki obiekt, kontroler tworzy z niego wbudowane zasoby i dopisuje status. Kontroler, który zna konkretną aplikację (jak odnowić certyfikat, jak przełączyć primary PostgreSQL), nazywamy operatorem.

CloudNativePG też ma typ Backup, ale w innej grupie: postgresql.cnpg.io. Dlatego nazwa CRD zawiera grupę (backups.postgresql.cnpg.io obok backups.szkolenie.example.com). Gdy dwie grupy mają ten sam typ, pisz pełną nazwę: kubectl get backups.postgresql.cnpg.io.

5 Anatomia CRD

Po lewej crd-backup.yaml z repo (bez komentarzy). Po prawej, co daje każda część.

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: backups.szkolenie.example.com   # <plural>.<group>
spec:
  group: szkolenie.example.com
  scope: Namespaced
  names:
    kind: Backup
    singular: backup
    plural: backups
    shortNames: [bk]
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            required: [schedule]
            properties:
              schedule:
                type: string
                description: Harmonogram w formacie cron, np. "0 2 * * *"
              retention:
                type: integer
                minimum: 1
                description: Ile kopii trzymać
    additionalPrinterColumns:
    - name: Schedule
      type: string
      jsonPath: .spec.schedule
    - name: Retention
      type: integer
      jsonPath: .spec.retention

Sam obiekt CustomResourceDefinition jest zawsze klastrowy, niezależnie od scope typu, który definiuje. scope nie zmienisz w istniejącym CRD.

Wersje: served i storage

CRD może mieć kilka wersji naraz, np. v1alpha1 i v1. Każda z served: true jest dostępna w API. Dokładnie jedna ma storage: true: w niej obiekty są zapisywane w etcd. Bez webhooka konwersji (conversion.strategy: None) kube-apiserver zmienia tylko pole apiVersion, więc schematy wersji muszą być zgodne. Przy zmianie struktury pól potrzebny jest webhook konwersji (strategy: Webhook), który dostarcza autor operatora. status.storedVersions w CRD pokazuje, w jakich wersjach coś kiedyś zapisano. Starą wersję oznaczysz deprecated: true, a kubectl wypisze wtedy ostrzeżenie.

Status, CEL i więcej kolumn: CRD gotowy na kontroler

Tego nie ma w repo. Tak wyglądałaby wersja v1 z kroku 3 symulatora:

  - name: v1
    served: true
    storage: true
    subresources:
      status: {}              # osobny endpoint /status
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            required: [schedule]
            x-kubernetes-validations:
            - rule: "!has(self.retention) || self.retention <= 30"
              message: "retention: najwyżej 30 kopii"
            properties:
              schedule: {type: string}
              retention: {type: integer, minimum: 1}
          status:
            type: object
            properties:
              cronJob: {type: string}
              observedGeneration: {type: integer}
    additionalPrinterColumns:
    - {name: Schedule, type: string, jsonPath: .spec.schedule}
    - {name: CronJob, type: string, jsonPath: .status.cronJob}
    - {name: Age, type: date, jsonPath: .metadata.creationTimestamp}
  • subresources.status oddziela spec od status. Zapis do głównego endpointu ignoruje zmiany w status, zapis do /status ignoruje zmiany w spec. Kontroler dostaje prawo do backups/status, użytkownik do backups. generation rośnie tylko przy zmianie spec.
  • Bez status w schemacie pole zostałoby usunięte przy zapisie (pruning). Dlatego nasz CRD bez kontrolera go nie ma.
  • subresources.scale (opcjonalnie) wskazuje pola z liczbą replik. Wtedy działa kubectl scale i HPA.
  • x-kubernetes-validations to reguły w języku CEL, liczone w kube-apiserverze (GA od 1.29). Sprawdzają zależności między polami, czego nie da się zapisać minimum czy required. Reguła z oldSelf, np. self == oldSelf, blokuje zmianę pola po utworzeniu.
  • additionalPrinterColumns po dodaniu własnych kolumn AGE trzeba dopisać samemu (type: date).

Odrzucenie przez CEL wygląda tak: The Backup "nightly" is invalid: spec: Invalid value: "object": retention: najwyżej 30 kopii.

6 RBAC i kto tworzy CRD

CRD: administrator klastra

  • customresourcedefinitions w grupie apiextensions.k8s.io to zasób klastrowy. Nowy typ widzą wszyscy w klastrze, a delete crd kasuje obiekty wszystkich.
  • Na naszym klastrze CRD backups.szkolenie.example.com wgrywa i usuwa trener. Ty możesz je czytać: kubectl get crd.
  • W firmie CRD instaluje zwykle zespół platformy razem z operatorem (chart Helm).

Obiekty Backup: Ty, w swoim namespace

  • Dla RBAC nowy typ to zasób backups (liczba mnoga) w grupie szkolenie.example.com.
  • Wbudowane role view, edit, admin nie znają nowego typu. Trzeba im go dokleić.
  • Trener dokleił reguły do edit (i admin), więc w swoim namespace tworzysz Backupy, a w cudzym nie. view nie dostało nic, dlatego get bk -A daje Ci forbidden.

Agregacja: ClusterRole doklejana do edit

# przyklady/k8s/20-crd/rbac-backups-edit.yaml (wgrywa trener)
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: szkolenie-backups-edit
  labels:
    rbac.authorization.k8s.io/aggregate-to-edit: "true"
    rbac.authorization.k8s.io/aggregate-to-admin: "true"
rules:
- apiGroups: ["szkolenie.example.com"]
  resources: ["backups"]
  verbs: ["get", "list", "watch", "create",
          "update", "patch", "delete"]

Role view, edit i admin mają aggregationRule: kontroler w kube-controller-manager dokleja do nich reguły z każdej ClusterRole z etykietą rbac.authorization.k8s.io/aggregate-to-<rola>: "true". Nikt nie musi zmieniać RoleBindingów kursantów. Operatory robią to samo w swoich chartach.

Kontroler potrzebuje własnej roli przez ServiceAccount, np. get, list, watch na backups, update, patch na backups/status i pełnych praw do cronjobs. Działa we wszystkich namespace'ach, więc to ClusterRole + ClusterRoleBinding.

kubectl auth can-i create backups              # yes
kubectl auth can-i create backups -n bartek    # no
kubectl auth can-i create customresourcedefinitions   # no

7 Pułapki i komendy

Pułapki

  • CRD bez kontrolera nic nie robi: żaden backup się nie wykona.
  • kubectl delete crd usuwa wszystkie obiekty tego typu we wszystkich namespace'ach, bez pytania. Odinstalowanie operatora razem z CRD = utrata wszystkich jego obiektów.
  • Nazwa CRD to zawsze <plural>.<group>.
  • forbidden … customresourcedefinitions: CRD tworzy administrator klastra.
  • helm upgrade nie aktualizuje CRD z katalogu crds/ charta. Wiele operatorów ma na to osobną flagę albo osobny chart.

Co dostajesz za darmo

  • REST, discovery, kubectl get/apply/delete, -o yaml, -w.
  • Walidację schematem i dokumentację w kubectl explain.
  • RBAC, audyt, admission (np. Kyverno) jak dla wbudowanych typów.
  • Watch, z którego korzystają kontrolery.
