1 · Architektura

Co gdzie stoi i kto komu wysyła dane

Stos observability działa w jednym namespace monitoring, wspólnym dla całej grupy; agenci zbierający logi i metryki węzłów działają na każdym węźle. Ty dokładasz obiekty tylko u siebie. Wybierz przepływ, żeby zobaczyć, którędy płyną dane, albo kliknij komponent. „Jedno żądanie” prowadzi krok po kroku przez dodanie zadania w ToDos.

ruch aplikacji metryki logi trace'y operator konfiguruje strzałka = kierunek, w którym płyną dane
2 · Sygnały

Trzy sygnały, trzy różne drogi

Każdy sygnał ma własnego agenta, własny magazyn i własny język zapytań. Łączą je wspólne etykiety (namespace, pod) i identyfikator trace_id.

Metrykimodel pull
kubelet / cAdvisor, kube-state-metrics, /metrics aplikacji←Prometheus pobiera co 30 s→PromQL w Grafanie

Prometheus sam odpytuje cele. Listę celów buduje Prometheus Operator z obiektów ServiceMonitor i PodMonitor. ToDos nie ma endpointu /metrics, więc dla niego masz metryki kontenera (CPU, pamięć, restarty), a po włączeniu trace'ów także span-metrics wyliczane przez Tempo.

Logistdout → agent na węźle
stdout / stderr kontenera→/var/log/pods na węźle→Alloy (DaemonSet)→Loki→LogQL

Aplikacja nie wie o Loki. Pisze na standardowe wyjście, a Alloy na każdym węźle czyta pliki logów i dokleja etykiety namespace, pod, container, app, node. Dlatego widzisz logi poda, którego już nie ma.

Trace'ymodel push, OTLP
SDK OpenTelemetry w procesie→OTLP/HTTP :4318→Tempo→TraceQL

Spany powstają wewnątrz procesu aplikacji, więc ktoś musi tam wstawić SDK. Kolejne serwisy łączą się w jeden trace dzięki nagłówkowi HTTP traceparent. Jak wstawić SDK, pokazuje następna sekcja.

3 · Instrumentacja

Skąd biorą się spany: cztery sposoby

Każdy sposób kończy się tak samo: span w formacie OTLP trafia do Tempo. Różnią się tym, gdzie span powstaje i kto musi coś zmienić. Wybierz sposób, a schemat pokaże, którą warstwę ruszasz.

W praktyce sposoby się łączy. Auto-instrumentacja (2 albo 3) daje szkielet: HTTP, bazy, kolejki. W kilku ważnych miejscach programista dopisuje ręczne spany biznesowe (1). Ręczny span z @opentelemetry/api podpina się pod SDK wstrzyknięte przez operatora.

7 · Instalacja

Jak postawiliśmy ten stos

Pięć chartów Helm, każdy z własnym plikiem wartości, w tej kolejności. U siebie (kind, własny klaster) zrobisz to samo; zmieniasz tylko klasę dysku i sposób wystawienia Grafany.

Repozytoria chartów

helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo add grafana             https://grafana.github.io/helm-charts
helm repo add grafana-community   https://grafana-community.github.io/helm-charts
helm repo add open-telemetry      https://open-telemetry.github.io/opentelemetry-helm-charts
helm repo update

Loki i Tempo są teraz w repo grafana-community; stare charty z grafana/ nie są rozwijane.

kube-prometheus-stack: Prometheus, Alertmanager, Grafana, operator

helm upgrade --install kube-prometheus-stack prometheus-community/kube-prometheus-stack \
  --version 92.10.1 -n monitoring --create-namespace -f kube-prometheus-stack.yaml --wait

W wartościach: retencja 7 dni, PVC na Prometheusa, hasło admina z Secretu, źródła danych Loki i Tempo dopisane do Grafany i połączone ze sobą (sekcja 3).

Selektory ServiceMonitorów są puste, więc Prometheus bierze obiekty ze wszystkich namespace'ów, nie tylko z etykietą release. Dzięki temu Twój ServiceMonitor zadziała bez dodatkowych etykiet.

Loki, Tempo, Alloy

helm upgrade --install loki  grafana-community/loki  --version 18.17.1 -n monitoring -f loki.yaml  --wait
helm upgrade --install tempo grafana-community/tempo --version 3.2.0   -n monitoring -f tempo.yaml --wait
helm upgrade --install alloy grafana/alloy           --version 1.13.1  -n monitoring -f alloy.yaml --wait

Loki w trybie single binary (jedna replika, dysk lokalny), Tempo z metrics generatorem (service-graphs, span-metrics, remote write do Prometheusa), Alloy jako DaemonSet z pipeline'em: format CRI → | json → etykieta level + trace_id.

Tryb single binary wystarcza do kilkudziesięciu GB logów dziennie. Produkcyjnie Loki w trybie rozproszonym z S3 jako magazynem.

OpenTelemetry Operator i obiekt Instrumentation

helm upgrade --install opentelemetry-operator open-telemetry/opentelemetry-operator \
  --version 0.124.1 -n monitoring -f opentelemetry-operator.yaml --wait
kubectl apply -f instrumentation.yaml        # Instrumentation "otel" → http://tempo.monitoring.svc:4318

Wymaga cert-managera: webhook operatora potrzebuje certyfikatu TLS.

Webhook dla podów ma failurePolicy: Ignore. Gdy operator nie działa, pody i tak wstają, tylko bez SDK. Przy Fail awaria operatora zablokowałaby tworzenie każdego poda w klastrze.

Grafana dla grupy: Ingress z TLS i konta

kubectl apply -f grafana-ingress.yaml        # host grafana.k8s.marniok.dev, ingressClass traefik, cert-manager
./grafana-kursanci.sh --edycja 2026-10-20 --loginy adamd,adamg,…   # konta z rolą Editor przez API Grafany

Rola Editor: Explore, własne dashboardy i alerty, bez zmian w źródłach danych i użytkownikach. Widzisz dane całego klastra, więc filtruj po swoim namespace.

Instalacja w trakcie zajęć. Stos stawialiśmy, gdy grupa robiła laby. Dwa ryzyka: limit pobrań z Docker Hub (wszystkie węzły wychodzą przez jeden NAT, a Grafana, Loki, Tempo i Alloy to obrazy z docker.io) oraz webhook OTel Operatora na wszystkie pody. W trakcie obserwowaliśmy kubectl get events -A -w | grep -iE 'pull|429'; błędów 429 nie było.
8 · Połączenia

Jak sygnały są ze sobą połączone

Sam zestaw trzech baz to jeszcze nie observability. Wartość jest w przejściach: z metryki do trace'a, z trace'a do logu i z logu do trace'a. Każde przejście to jedno ustawienie w źródłach danych Grafany.

Log → traceLoki · derivedFields

Pole trace_id w linii logu (structured metadata z Alloy) staje się linkiem do Tempo. Warunek: aplikacja loguje trace_id.

Trace → logiTempo · tracesToLogsV2

Przycisk „Logs for this span” szuka w Loki logów z etykietą app = service.name spana i z tym trace_id, ±5 min.

Metryka → tracePrometheus · exemplary

Kropki na wykresie latencji z trace_id przykładowego żądania. Wymaga aplikacji, która wystawia exemplary.

Mapa usług (Service Graph) i span-metrics nie wymagają nic w aplikacji: liczy je Tempo z samych spanów i wysyła do Prometheusa jako traces_service_graph_* i traces_spanmetrics_*.
9 · Słowniczek

Pojęcia, które padną w Grafanie

trace
Historia jednego żądania przez wszystkie serwisy: drzewo spanów z jednym trace_id.
span
Jeden krok w trace: wywołanie HTTP, zapytanie do bazy, funkcja. Ma początek, czas trwania, atrybuty i rodzica.
traceparent
Nagłówek HTTP (W3C Trace Context) z trace_id i id spana rodzica. Serwis, który go nie przekaże, przerywa trace.
OTLP
Protokół OpenTelemetry dla metryk, logów i trace'ów. Port 4317 to gRPC, 4318 to HTTP.
scrape
Pobranie metryk przez Prometheusa z adresu /metrics celu. Domyślnie co 30 s.
ServiceMonitor
Obiekt CRD Prometheus Operatora: „zbieraj metryki z Service'ów o tych etykietach, z tego portu”.
kardynalność
Liczba różnych kombinacji etykiet. user_id albo trace_id jako etykieta tworzy miliony serii i zabija Prometheusa i Loki.
span-metrics
Metryki wyliczane przez Tempo z napływających spanów: liczba żądań, czasy, błędy. Metryki RED bez /metrics w aplikacji.
mutating webhook
Mechanizm API Kubernetesa, którym operator zmienia obiekt przed zapisem. Tak OpenTelemetry Operator dokłada init container i zmienne do Twojego poda.
Klaster szkoleniowy k8s-sages (EKS, eu-central-1). Stos: kube-prometheus-stack, Loki, Tempo, Grafana Alloy, OpenTelemetry Operator, wszystko w namespace monitoring.
