GitOps z Argo CD a zwykły pipeline

Pipeline CI/CD wypycha zmianę do klastra i kończy pracę. Argo CD siedzi w klastrze, sam pobiera stan z gita i bez końca pilnuje, żeby klaster się z nim zgadzał. Ta ściąga pokazuje oba modele krok po kroku, co się dzieje przy ręcznej zmianie i co realnie zyskujesz, a co tracisz.

1 Dwa modele obok siebie

W obu modelach CI robi to samo na początku: testy, build obrazu, push do rejestru. Różnica jest w ostatnim kroku. Kto wgrywa zmianę do klastra i czy ktoś patrzy na klaster potem?

Push: klasyczny pipeline (GitHub Actions, GitLab CI)

Pull: GitOps z Argo CD

Argo CD nie „nasłuchuje na push”. To pętla rekoncyliacji, ta sama idea co kontroler i operator z dnia 4 (pętla kontrolera): obserwuj, porównaj stan zadany (git) z rzeczywistym (klaster), działaj. Webhook z GitHuba tylko przyspiesza krok „obserwuj” po stronie gita. Bez niego wszystko działa tak samo, tylko wolniej.

2 Pętla rekoncyliacji i drift: symulator

Drift to różnica między tym, co jest w gicie, a tym, co działa w klastrze. Powstaje, gdy ktoś zmieni coś ręcznie (kubectl scale, edit, delete). Wybierz tryb i klikaj akcje. Zobacz, kto zauważy zmianę i kto ją cofnie. Aplikacja to podinfo-prod z przykładu 29: 2 repliki, tag 6.14.1, napis prod v1.

Dwa statusy Argo CD warto czytać osobno. Sync: czy klaster zgadza się z gitem (Synced / OutOfSync). Health: czy to, co działa, jest zdrowe (Healthy, Progressing w trakcie rolloutu, Degraded przy błędzie, Missing gdy zasobu brak). Aplikacja może być Synced i Degraded naraz: w gicie jest zły tag, Argo CD wiernie go wdrożył.

3 Obiekt Application

Application to CRD Argo CD. Mówi: „pilnuj, żeby w tym klastrze i namespace było to, co w tym repo pod tą ścieżką”. Po lewej application.yaml z przykładu 29. Najedź albo kliknij podświetlone pole.

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: podinfo-prod
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io/background
spec:
  project: default
  source:
    repoURL: https://github.com/dawid-marniok/kubernetes-w-praktyce.git
    targetRevision: main
    path: przyklady/k8s/29-gitops-argocd/app
    helm:
      valueFiles:
        - values-prod.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: gitops-demo
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true

Helm w Argo CD to nie helm install

  • Argo CD tylko renderuje chart (helm template) i sam robi apply. Release'u Helma nie ma.
  • helm list -n gitops-demo jest pusty. Nie ma Secretów sh.helm.release.v1.*.
  • helm rollback nie działa. Historia = git log + zakładka History and Rollback w UI.
  • Rollback = git revert i push. Rollback z UI jest możliwy tylko bez automated (inaczej Argo CD od razu wróci do gita).
  • Hooki Helma (helm.sh/hook: pre-install itd.) Argo CD tłumaczy na swoje hooki (PreSync, PostSync).
  • lookup w szablonach zwraca pusto: repo-server nie pyta klastra.
  • Flux dla porównania robi prawdziwy helm install / upgrade przez obiekt HelmRelease. Tam helm list pokazuje release.

4 Kto ma klucze do klastra

Najważniejsza różnica dla bezpieczeństwa. W push to CI wchodzi do klastra, więc CI musi mieć klucze. W pull klaster sam wychodzi po zmiany, a CI dostaje tylko prawo zapisu do repo.

Sprawdź, co dostaje ktoś, kto przejmie jeden element:

Na EKS

  • Push: pipeline potrzebuje roli IAM z dostępem do klastra (access entry z polityką, np. AmazonEKSClusterAdminPolicy albo zawężoną do namespace'ów). Lepiej przez OIDC z GitHub Actions (rola bez stałych kluczy) niż przez klucze w sekretach. Endpoint API klastra musi być osiągalny z runnera: publiczny albo runner we własnym VPC.
  • Pull: Argo CD używa swojego ServiceAccountu w klastrze. CI ma tylko rolę do push w ECR i token do repo. Endpoint klastra może być prywatny.
  • Prawo zapisu do repo konfiguracji i tak jest „prawie” dostępem do klastra: kto zmerguje commit, ten wdraża. Dlatego branch protection i review są częścią bezpieczeństwa.

6 Kiedy co

Model mieszany (najczęściej)

  • CI: testy, build, push obrazu, commit z nowym tagiem do repo konfiguracji.
  • Argo CD: wdraża i pilnuje.
  • CI nie ma kluczy do klastra, a zespół dalej ma szybkie testy i build w znanym miejscu.

Push wystarczy

  • Jeden klaster, mały zespół.
  • Mało środowisk, rzadkie wdrożenia.
  • Nikt nie zmienia klastra ręcznie albo drift nie boli.
  • Nie ma kogo posadzić do utrzymania Argo CD.

GitOps się opłaca

  • Wiele środowisk i klastrów.
  • Audyt, regulacje, „kto i kiedy zmienił produkcję”.
  • Drift jest realnym problemem.
  • Nie chcesz trzymać kluczy do produkcji w CI.
  • Chcesz odtwarzać klaster z gita.
